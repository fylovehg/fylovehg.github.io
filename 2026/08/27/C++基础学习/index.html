动态内存分配

  • 动态内存本质：向操作系统申请一块内存，操作系统只返回起始地址；怎么解读这块内存，由代码里的指针类型决定。

为什么需要动态内存？

普通数组int arr[100]是静态数组：编译期就要确定常量大小，提前把内存占住。

  • 缺点：空间浪费；如果需求数量不确定（游戏副本随机刷 100‑10000 个怪物），直接定义超大数组会耗尽内存。
  • 动态内存：运行时需要多少就申请多少，用完归还，更智能。

类比分房：静态数组直接一次性分 100 套房，住不住都占着；动态内存需要多少套申请多少，退房还给物业。

⚠️边界：操作系统返回仅仅是起始地址，不能越界访问；访问分配以外的内存，程序异常崩溃。

C 语言动态内存函数（<stdlib.h>）

  1. malloc(size_t size)
  • 参数：size_t无符号整数，需要分配的字节总大小
  • 返回值：void*空类型指针，只保存地址，没有绑定类型；分配失败返回NULL(0)。
  • 使用：需要强制转换成对应类型指针；不会初始化内存，里面是残留垃圾值。

注意：变长数组int arr[x]部分编译器支持，但不是标准 C，有坑，优先动态内存。

  1. calloc(size_t num, size_t size)
  • 参数：num元素个数，size单个元素字节大小，内部自动计算总字节num*size
  • 返回：void*，失败返回NULL
  • 和malloc最大区别：分配完自动把整块内存全部清零
  • 代价：清零操作消耗 CPU，效率略低于malloc
  1. realloc(void* ptr, size_t new_size) 重新扩容 / 缩容

对已经分配好的内存调整大小。
两种工作场景：

  1. 原内存后方有空闲内存：直接原地扩容，指针地址不变，原有数据保留。
  2. 后方被占用：操作系统在内存别的地方开辟一块全新内存，把旧内存的数据拷贝过来，返回全新地址，旧内存自动回收。

⚠️不要直接写 p = realloc(p, new_size);，如果分配失败返回 NULL，会直接把原来有效内存地址覆盖丢失。
规范写法：先用临时指针接收返回值。

  1. free(void* ptr) —— 释放内存

有借有还，用完动态内存必须 free，否则造成内存泄漏。

⚠️重点坑点：

  1. free只归还内存给操作系统，指针变量本身的值不会自动置 0，变成悬挂指针：指针保存旧地址，但这块内存已经不属于程序。后续访问悬挂指针程序崩溃。
    • 最佳实践：free(p); p = NULL;
  2. 不能重复 free 同一个指针，程序直接异常。
  3. free 只能释放 malloc/calloc/realloc 返回的地址，不能释放普通栈上变量地址。

C++ 动态内存 new /delete

底层本质：C++ 的new/delete底层封装调用 C 的malloc/free。

1️⃣ new

  1. 分配单个对象
  1. 分配数组（运行时动态数量）

2️⃣ delete（释放，必须配对！）

✅配对规则：

  • new 类型 → delete p;
  • new 类型[数量] → delete[] p;

❗错配会引发未定义行为，程序崩溃。

C++17 推荐空指针字面量nullptr，代替 0；C 语言只能使用 0 代表空指针。

C vs C++ 动态内存对比

  1. C：malloc/calloc/realloc/free，返回void*，需要手动强制类型转换。
  2. C++：new/delete，自动匹配类型，不用强制转换；数组释放必须带[]。

注意：不要混用！malloc出来的内存不能用delete释放；new出来的内存不能用free释放。

  • 常见坑汇总
  1. 内存分配不判 NULL：内存耗尽得到空指针，解引用直接崩溃。
  2. 越界访问动态内存：读写超出申请字节，破坏其他内存，程序异常。
  3. 内存泄漏：malloc/new 申请内存，忘记 free/delete，程序长期运行内存越来越高。
  4. 悬挂指针：free/delete 之后继续使用旧指针；建议释放后立刻置空。
  5. 重复释放：多次 free 同一个指针，未定义行为。
  6. new [] 对应 delete，或者 new 对应 delete []：配对错误。
  7. C 语言不要指望变长数组int arr[n]做动态数组，可移植性差。

C++动态内存风险

动态内存的风险点

  • C/C++动态内存灵活强大,但也是最难调试Bug的来源,快乐和坑都来自堆内存.
  • （1）. 悬挂指针（野指针）

内存已经free/delete释放还给操作系统，但指针变量仍然保存原来的地址，继续使用该指针。

  1. 现象：不一定崩溃报错，可能正常运行，属于静默故障，最难排查。就像退房之后还继续使用已经退掉的房间。
  2. C：malloc申请，free(p)释放，释放后p就是悬挂指针。
  3. C++：new / new[]申请，对应delete / delete[]释放。
    • 配对规则必须严格一对一
      • new int → delete p;
      • new int[N] → delete[] p;
    • 混用现在简单类型可能看不出问题，面向对象类对象一定会出错。
  4. 衍生问题：重复释放
    • 对同一块内存多次free/delete。
    • 多线程场景容易出现：A 释放内存，内存被 B 重新申请占用，A 再次释放，相当于释放别人正在使用的内存。
    • 重复释放不一定崩溃，静默错误非常危险。
  5. 编码建议：释放之后，手动把指针置空 p = nullptr;，只能靠编码规范规避，编译器无法全部拦截。

⚠️禁止混用分配释放接口

  • malloc分配的内存，不要用delete释放；

  • new分配内存，不要用free释放。
    底层虽然部分实现上 new 基于 malloc，但 C++ 对象会调用构造析构函数，混用会破坏对象生命周期，普通 int 侥幸不出错，类对象直接出严重 bug。

  • （2）. 内存碎片

堆内存分配要求必须连续内存块。

  1. 成因：频繁小块内存申请、释放。空闲内存总量充足，但是全部是零散小块，没有足够大的连续空闲块，申请大块内存失败。
  2. 场景：
    • PC 桌面：64 位系统虚拟地址空间巨大，new/delete 底层内存分配器会做合并优化，碎片问题一般不明显。
    • 嵌入式设备（手环、单片机）内存很小，碎片是高频坑。
  3. 高级方案：内存池，手动整理内存移动数据合并碎片（本课程不展开）。

  1. 老式写法（直接用 new）
  1. C++14 推荐写法：std::make_unique

圆括号的语义完全不同，这是 C++ 设计上被吐槽的点之一。

访问方式：单对象 vs 数组

这是 unique_ptr 比原生指针 “智能” 的地方之一：在编译期就阻止了你用错访问方式。原生指针 int* a 既可以 *a 也可以 a[0]，编译器不管，运行时才崩。

核心特性：唯一性（不可复制）

为什么？ 因为如果允许多个 unique_ptr 指向同一块内存，析构时就会重复释放（double free）。唯一性从根源上杜绝了这个问题。

四个常用成员函数

  1. reset() — 释放内存并置空

效果等同于 delete ptr; ptr = nullptr;，但你不需要手动写。

  1. get() — 获取内部原生指针（不释放所有权）

用途：某些旧 API 只接受原生指针时，临时拿出来用一下。不要 delete 返回的指针，否则会 double free。

  1. release() — 放弃所有权但不释放内存

表格

reset() release()
释放内存？ ✅ 是 ❌ 否
内部指针置空？ ✅ 是 ✅ 是
返回值 无 原生指针地址

讲师说 “release 听起来像释放但其实不释放内存”—— 这个提醒很重要，很多人在这里踩坑。

  1. std::move() — 转移所有权（”过户”）

过户前后对比：

表格

过户前 过户后
a 指向内存地址 nullptr（空）
b nullptr 指向原内存地址

这是 unique_ptr 唯一的 “转移” 方式，保证任意时刻只有一个所有者。

为什么 unique_ptr 更安全

  1. 不会重复释放 — 唯一性保证只有一个所有者，析构时只释放一次
  2. 不会悬挂指针 — 原生指针可以随意复制，delete a 后 b 还指向已释放内存（悬挂）；unique_ptr 不允许复制，从语法上消灭了这个场景
  3. 自动释放 — 离开作用域自动调用析构函数释放内存，不需要手动 delete

shared_ptr vs unique_ptr 核心区别

表格

unique_ptr shared_ptr
所有权 独占（一夫一妻制） 共享（共享单车）
同一块内存可被几个指针指向 1 个 N 个
拷贝 / 赋值 ❌ 禁止（编译报错） ✅ 允许
内存释放时机 该指针析构 /reset 时立即释放 最后一个持有者释放时才释放
额外开销 几乎无 有引用计数（线程安全的原子操作）

讲师的类比很到位：unique_ptr 像私人车，你不用了就直接报废；shared_ptr 像共享单车，你退卡了车还在，直到最后一个人退卡才把车砸了。

声明与初始化

  1. 直接用 new（老式写法，支持数组）
  1. std::make_shared（推荐写法）

⚠️ 关键限制：make_shared 不支持数组

讲师反复强调：std::make_shared<int[]>(5) 在 C++11/14 下编译报错。

补充（讲师没说）：C++20 起 std::make_shared 已支持数组，写法为 std::make_shared<int[]>(5)。但如果你用 C++14/17，要数组只能用 new 的老式写法，或者用 std::vector 替代。

共享：可以随意拷贝赋值

这是和 unique_ptr 最直观的区别 ——unique_ptr 这里直接编译报错。

引用计数机制（核心原理）

shared_ptr 内部维护一个引用计数（reference count），记录当前有多少个 shared_ptr 指向同一块内存。

  • 每新增一个拷贝 → 计数 +1
  • 每释放一个（reset / 析构）→ 计数 -1
  • 当计数降到 0 时，才真正释放内存

use_count() — 查看当前引用计数

返回值类型是 long。所有指向同一内存的 shared_ptr 调用 use_count() 结果相同。

reset() 的行为（和 unique_ptr 不同！）

表格

unique_ptr::reset() shared_ptr::reset()
释放内存？ ✅ 总是立即释放 ⚠️ 仅当是最后一个持有者时才释放
自身置空？ ✅ 是 ✅ 是

讲师演示中 reset 后再访问该指针会崩溃（地址已变为 0），但只要还有其他持有者，内存本身还在，其他指针仍能正常读出值 5。

字符串（char str[]）

字符串的本质

字符串 = 一串字符，在内存中连续存储。

为什么必须以 \0（零）结尾？

内存里全是数字，如果你不标记 “字符串到这里结束”，程序就不知道该读到哪里 —— 会把后面不属于这个字符串的内存也一起读出来，导致越界访问和乱码。

讲师说的 “杠铃” 就是 \0，空字符（null terminator），ASCII 值为 0。

字符的两种类型

字符串的三种声明方式（char 版）

  • 方式 1：数组逐个字符初始化（繁琐，不推荐）
  • 方式 2：数组 + 字符串字面量（推荐）

"hello" 的本质是 const char[6]，编译器帮你把每个字符填好并自动加 \0。

  • 方式 3：指针指向字符串字面量
  • 方式 4：动态申请（new）

中文在内存中的表现（GBK 编码）

中文操作系统默认使用 GBK 编码（代码页 936），每个中文字符占 2 字节。

  • 英文：1 字节 / 字符
  • 中文：2 字节 / 字符
  • 结尾：1 字节的 \0

这就是老程序员常说的 “中文两个字节，英文一个字节，两个英文顶一个中文”。

宽字节字符串&字符（wchar_t）

wchar_t 统一用 2 字节表示一个字符（Windows 下 UTF-16），中英文都是 2 字节。

声明以及打印的方式

内存布局（UTF-16，小端序）

  • 每个字符固定 2 字节
  • \0 也是 2 字节：0x0000
  • 中文使用 Unicode 码点，不是 GBK

显示：用 wcout，不是 cout

讲师演示中 “hello 出来了，张三没出来”，就是因为控制台默认用 GBK 解码 UTF-16 的数据，对不上就显示不出来。设置 locale 后告诉控制台 “用 Unicode 解码”，就能正常显示了。

编码表的核心概念（为什么会乱码）

文字 ↔ 数字 的映射由编码表决定。 同一段数字，用不同的表翻译，结果完全不同。

表格

乱码的本质：写入时用的编码表 ≠ 读取时用的编码表。

指针与结构体

结构体内存对齐问题

CPU 访问内存不是 1 字节 1 字节读的，而是按 4 字节或 8 字节为单位整块读取。如果一个 int（4 字节）横跨了两个读取块，CPU 就要读两次再拼接，效率低；某些硬件平台直接崩溃。

对齐的本质就是在成员之间插入空字节（padding），让每个成员 “排好队”，方便 CPU 一次读完。

核心规则

1：成员偏移量必须是自身大小的整数倍

表格

类型 大小 偏移量必须是
char 1 任意位置（1 的整数倍）
short 2 0, 2, 4, 6…
int 4 0, 4, 8, 12…
long 8（64 位） 0, 8, 16…
double 8 0, 8, 16…
指针 8（64 位） 0, 8, 16…

2：结构体总大小必须是最大成员大小的整数倍

如果最后一个成员结束后不够，在末尾补空字节。

3：成员按声明顺序依次排列，不能重排

编译器不会帮你调换成员顺序，你声明的顺序就是内存中的顺序。

五、注意事项（坑很多）

坑 1：同一时间只能用一个成员

写了哪个成员，就只能读哪个成员。交叉读写结果不确定。

坑 2：初始化只能初始化第一个成员

C++11 以后可以用花括号指定，但默认还是初始化第一个。

坑 3：不能有引用类型、虚函数、继承

union 不支持面向对象的那些特性，它就是一块原始内存的不同视图。

坑 4：含非平凡构造函数的成员（C++11 前禁止）

如果 union 里有 std::string 这种需要构造 / 析构的成员，你必须手动调用 placement new 构造、手动调用析构函数，非常麻烦。实际开发中尽量别在 union 里放复杂对象。

坑 5：匿名 union

匿名 union 的成员直接暴露在外层作用域，用起来更简洁，但要注意命名冲突。
