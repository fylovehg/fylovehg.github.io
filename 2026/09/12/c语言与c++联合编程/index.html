§1 静态变量 static

在普通变量声明前加上 static 关键字，就得到一个静态变量。它解决的是「函数结束后，变量还在不在」的问题。

语法

特性

  • 只初始化一次：整个程序运行期间只初始化一次，之后每次进入声明它的函数，都不会再执行初始化语句。
  • 自动初始化为 0：声明时不指定初始值，编译器自动初始化为 0（与普通局部变量「不初始化就是随机值」完全不同）。
  • 生命周期与全局变量相同：程序启动时创建，程序结束时销毁；不因函数返回而消失。
  • 作用域不变：仍是局部变量，只能在声明它的函数内访问；存储位置不在栈上，而是放在全局（静态）存储区。

对比

对比项 普通局部变量 静态局部变量 全局变量
初始化 不初始化则为随机值 自动初始化为 0（只一次） 自动初始化为 0
生命周期 函数结束即销毁 程序结束才销毁 程序结束才销毁
作用域 所在函数内 所在函数内 整个程序（多文件）
存储位置 栈区 全局（静态）存储区 全局（静态）存储区

警告：「只初始化一次」不是「值不变」：每次进入函数仍会执行函数体内其他语句，只是初始化语句不再执行。static 扩大的是生命周期，不是作用域。

§2 内联函数 inline

在函数声明（或定义）前加上 inline 关键字，是告诉编译器：最好把这个函数「内联」处理。它解决的是「小函数调用开销值不值」的问题。

语法

原理

普通函数调用在汇编层面要做：参数压栈（push）、call 跳转、恢复栈帧、返回后恢复栈平衡。内联函数则把函数体代码直接展开到调用处，省掉压栈、出栈和跳转的开销。

适用条件

  • 函数体只有一两行（如 return a + b;）时，入栈/出栈的固定开销占比大，内联收益明显；
  • 函数体几千行时，固定开销可以忽略，内联没有意义。

备注：inline 只是「建议」不是命令，编译器有权忽略。现代编译器优化能力强，甚至会做常量折叠（把 add(1, 2) 直接算成 3），因此 inline 在现代 C++ 中相对「鸡肋」，了解即可。

警告：inline 函数不能递归：递归函数无法在编译期展开成有限代码，编译器不会采纳内联建议（详见 §8 递归函数）。

§3 声明与定义

「声明（declaration）」和「定义（definition）」是 C/C++ 最基础也最容易被忽视的概念。多文件工程里各种「找不到标识符」「重定义」「无法解析的外部符号」错误，根源几乎都在这里。

为什么必须先声明后使用

编译器从第一行往后逐行翻译。遇到 ave(12, 8) 这样的调用时，它必须先知道 ave 的返回类型和参数类型，否则无法生成调用代码，报「找不到标识符」。解决办法就是在调用之前先给出声明。

声明与定义的区别

对比项 声明 declaration 定义 definition
作用对象 编译器 计算机（通过编译器翻译）
内容 签名：返回类型 + 参数类型 签名 + 函数体（实现）
内存分配 不分配 分配
出现次数 可以多次 只能一次
变量写法 extern int a; int a = 25;
函数写法 int ave(int, int); int ave(int a, int b) { ... }

备注：记忆口诀：声明是「我们和编译器之间的事」（为了让编译通过）；定义是「我们通过编译器告诉计算机的事」（真正分配内存、产生机器代码）。函数声明中的参数名可以省略（int ave(int, int); 合法），但写上更利于阅读。

示例：先声明、后定义

3.1 变量的声明与定义：extern

变量默认写法 int a = 25; 或 int a; 都是「定义」——因为要分配内存。只想声明全局变量而不定义，必须使用 extern：

  • 函数默认就是 extern：函数声明即使不写 extern 也按 extern 处理（「声明可多次」正是基于此）；变量不加 extern 时默认视为定义。
  • extern 只作用于全局：函数体内用 extern 声明局部变量会报「重定义」错误。
  • 意义：库作者给别人看头文件时，别人只需看到声明；真正分配内存的定义放在某个源文件中。

3.2 程序的内存布局

理解「定义分配内存」的底层含义，需要知道程序的内存长什么样。

  • 4GB 虚拟地址空间：32 位进程默认拥有 2³² = 4GB 虚拟地址空间，与物理内存大小无关；超出实际内存的部分通过「内存交换」换到硬盘，所以内存被撑爆后程序会明显变卡。
  • 地址空间划分：低地址空指针区（0x00000000 附近，访问即崩溃，这是空指针解引用的本质）→ 用户区 → 内核区（0x80000000 以上，操作系统使用）。
  • 用户区四分区：全局变量区（全局变量和 static 变量）、代码区（函数二进制代码）、栈区（局部变量）、堆区（自由存储区，new/malloc 动态分配）。
  • 固定地址：全局变量和函数在编译期分配相对固定地址（加载后只做很小基址偏移）；局部变量每次调用都在栈上动态分配，没有固定地址。

备注：因为全局变量、函数地址相对固定，逆向时很容易被定位（如游戏外挂通过固定地址读写全局数据）；这也提示：不要把数据都放到全局区。

警告：「找不到标识符」＝编译器在调用点之前没见过该函数的声明/定义，不一定是函数不存在；声明写 100 次没事，定义写 2 次必错——这是多文件工程「重定义」错误的总根源。

§4 头文件与源文件

一个人盖不了摩天大楼，所以要分工；一个大型项目有几万个函数，不可能写在一个文件里。模块化就是把代码拆到多个文件，再用头文件把它们「拼接」起来。

源文件与编译流程

  • .cpp 是 C++ 源文件，.c 是 C 源文件；.c 文件要用 C 语法（printf/scanf，需 stdio.h）。
  • 编译器只编译源文件：每个 .cpp 单独编译成目标文件 .obj，最后把所有 .obj 链接成可执行文件 .exe。
  • #include "xxx.h" 的作用，是把 xxx.h 的完整内容复制到当前源文件中再一起编译；头文件本身不会被单独编译。

备注：推论：头文件里写有明显语法错误的代码，只要没有源文件包含它，工程仍能编译通过；一旦某个源文件 #include 了它，编译立刻报错。

实践：把自己的函数组织成「源文件 + 头文件」

头文件里能放定义吗

  • 语法上可以，工程上不行：头文件被复制进每一个包含它的源文件，普通函数定义会被复制多份，链接时报「重定义」。
  • 两个例外：static 变量/函数（内部链接，每个源文件各一份独立内存空间，互不冲突）和 inline 函数（同样允许）。
  • 跨文件共享全局变量：定义只能写一次（放某个源文件），其他源文件用 extern 声明引用；extern 声明不能带初始化值。

4.1 防止头文件被重复包含

同一个头文件可能被多个头文件间接包含多次，每个头文件都应加「防止重复包含」保护，两种写法：

对比项 #pragma once #ifndef 宏保护
标准性 非标准指令 C/C++ 标准预处理器指令
写法 一行 三行（#ifndef/#define/#endif）
宏名冲突风险 无 有（宏名需全工程唯一）
支持的编译器 多数现代编译器 所有编译器

警告：两种保护都只对「单个源文件内的重复包含」有效，不是「整个工程只编译一次」——不同源文件包含同一头文件，各自仍展开一份，所以头文件里依然不能放普通函数定义。#ifndef 的宏名若与其他头文件撞名，后包含的内容会被整个跳过，报「找不到标识符」。

4.2 条件编译：#if / #ifdef / #ifndef

#ifdef：定义了宏就编译其中的代码；#ifndef：没定义才编译。它们在编译期起作用——不满足条件的代码，编译器根本不会编译。

提示：典型应用是版本管理：同一份源码通过是否定义宏，编译出「VIP 版」和「普通版」两份程序，未定义宏对应的代码不会进入可执行文件，产物大小也会明显不同。另注意：#include 尖括号与双引号查找路径不同——尖括号在编译器的包含目录中查找，双引号优先在当前目录查找。

§5 C 与 C++ 混用：extern “C”

大型项目里可能既有老的 C 风格代码，又有新的 C++ 代码。但 C 和 C++ 对函数名的处理方式不同，直接混用会链接失败。

问题的根源：名字修饰

  • C++：函数名被修饰。C++ 支持重载，编译器编译时把函数名「修饰」成带参数信息的符号（如 ?ave@@YAHHH@Z 这类乱码式符号名）。
  • C：函数名保持原样。C 不支持重载，编译后的符号就是函数名本身（如下划线 + 函数名 _ave）。
  • 症状：C++ 源文件调用定义在 .c 文件中的函数时，C++ 按修饰后符号去找，而 .c 产生的是未修饰符号，两头对不上 → 「无法解析的外部符号」。

警告：extern "C" 只解决「C++ 调用 C 函数」的方向；反过来，.c 文件无法调用 C++ 函数（C 编译器不认识 C++ 修饰符号），只能把 C++ 函数声明成 C 风格来迁就。且被 extern "C" 包裹的函数不支持重载——重载依赖名字修饰，C 风格函数不修饰名字。

§6 静态库与项目模板

用过的 printf、STL 都来自别人封装好的库。这一节把前面的知识串起来：自己做函数 → 打包成静态库 → 配置给其他人用 → 把工程导出成项目模板。

什么是库 / SDK

库就是「实现 + 声明」的打包：把函数实现编译成 .lib（静态库）文件，头文件作为说明书一起发布。把库、文档、示例程序打包发布，就构成 SDK。版本号等常量应在头文件开头用 const 常量定义，并可以把函数、变量、常量装进自己的命名空间（模仿 std），避免与使用者的名字冲突。

制作静态库的步骤

步骤 做什么 产物/要点
1 写实现 新建源文件 MyLib.cpp，实现各函数 函数定义（实现）
2 写声明 新建头文件 MyLib.h，放全部函数声明 函数声明（说明书）
3 改配置 工程属性 → 常规 → 配置类型 → 静态库(.lib) 不再生成 .exe
4 生成 生成解决方案 得到 MyLib.lib
5 发布 发布 .lib + .h（+ 示例程序/文档） 别人拿到即可用

使用静态库的三步配置

  1. 包含目录：把头文件所在目录加入「VC++ 目录 → 包含目录」（对应 #include <xxx.h> 尖括号查找路径）。
  2. 库目录：把 .lib 所在目录加入「VC++ 目录 → 库目录」。
  3. 指定链接的库：代码里写 #pragma comment(lib, "MyLib.lib")；或在工程属性 → 链接器 → 输入 → 附加依赖项中填写库名（多个库用分号分隔）。

备注：记忆：包含目录让编译器找到「声明」，库目录 + 链接器配置让链接器找到「实现」。缺一步分别报「找不到头文件」或「无法解析的外部符号」。

导出项目模板

  • 用途：把配置好依赖（包含目录、库目录、链接器设置）的工程导出成模板，以后新建项目选这个模板，环境自动配好。
  • 导出：项目 → 导出模板 → 项目模板 → 填写模板名称 → 勾选「自动导入」。生成一个与模板同名的 .zip 文件。
  • 发布：把 .zip 拷贝到 我的文档\Visual Studio 2019\Templates\ProjectTemplates（或其 C++ 子目录），重启后新建项目即可看到；发布给他人同理。
  • 注意：模板中不要写死绝对路径，包含目录、库目录应改用相对路径（如 $(ProjectDir) 等宏），保证模板可移植。

提示：典型应用：游戏引擎基础工程（俄罗斯方块、贪吃蛇共用的配置与基础代码）、SDK 发布——用户创建项目即自带全部环境。#pragma comment(lib, ...) 是 MSVC 专有写法，跨编译器工程用「链接器附加依赖项」或构建脚本更通用。

§7 函数调用约定

函数调用在机器层面要解决两件事：参数怎么传递、栈平衡由谁来恢复。调用者与被调用函数之间关于这两件事的「协议」，就是调用约定。

背景

参数通过栈传递（默认从右到左压栈），压栈破坏了栈平衡，函数返回后必须恢复（普通函数调用后常见 add esp, 8 之类的指令）。约定不同，参数传递方式、栈平衡恢复方、编译后的符号都不同。x86（32 位）下常见三种：

__cdecl（默认约定）

  • 参数从右到左入栈；栈平衡由调用者恢复（谁调用谁负责清理）。
  • 因为调用者知道自己压了几个参数，支持不定参数——printf 就是典型的 __cdecl 函数。
  • 默认不写就是它。

__stdcall

  • 参数从右到左入栈；栈平衡由被调函数自己恢复（函数内部用 ret n 清理）。
  • 被调函数不知道调用者压了几个参数，不支持不定参数。
  • 符号名形如 _函数名@参数总字节数（如 _add@8）；Win32 API 大量使用。

__fastcall

  • 前两个参数通过寄存器传递（依次放入 ECX、EDX），其余参数仍压栈；寄存器在 CPU 内部，比访问内存快。
  • 剩余参数的栈平衡由被调函数恢复。
  • x86 下默认是 __cdecl；x64 架构下默认约定相当于 fastcall 家族（细节不同）。

备注：naked：不生成编译器自动添加的序言/尾声代码，几乎不用，只在驱动开发等特殊场景出现。

对比项 __cdecl __stdcall __fastcall
参数传递 栈（从右到左） 栈（从右到左） 前两个用寄存器 ECX/EDX，其余入栈
栈平衡恢复方 调用者 被调函数 被调函数
不定参数支持 支持（如 printf） 不支持 不支持
符号形式 _函数名 _函数名@参数字节数 @函数名@…
典型场景 默认约定、C 函数 Win32 API x64 默认（类似）

警告：看到「无法解析的外部符号」时，除了查名字修饰，还要注意调用约定不一致（如一边 __cdecl 一边 __stdcall）也会导致符号对不上。不定参数函数只能是 __cdecl；寄存器传参只对前两个参数有效，参数更多时依然走栈。

§8 递归函数

递归函数是在函数体内调用它自己的函数——像蛇咬住自己的尾巴。它并不特殊，只是多了一个「不该做的操作」：调用自身。

定义与退出机制

递归函数是「自己控制退出」的循环，必须设计好结束条件；没有结束条件的递归会变成死递归，最终导致程序崩溃。

示例：用递归求 1 到 x 的和

执行过程：sum(10) = 10 + sum(9) = 10 + 9 + sum(8) = … 一路展开到 sum(1) = 1，再逐层回代，最终得到 55。

栈溢出：为什么死递归会崩溃

  • 函数每一次调用都会创建栈帧（压栈、传参）。递归每深入一层就压一个栈帧，直到把栈空间耗尽——栈溢出，程序直接崩溃。
  • 循环卡住只是程序不响应；多线程中最多卡住一条线程。递归一旦失控是必然的栈溢出崩溃，且影响整个进程。
  • 递归每层都有函数调用开销（压栈、传参、恢复栈平衡），执行效率低于等价循环；但代码量少、逻辑清晰，可读性强。
对比项 递归 循环
代码量 少、简洁 相对多
可读性 结构清晰（尤其树形问题） 一般
执行效率 低（每次调用压栈传参） 高
失控后果 栈溢出、程序崩溃 卡住（单线程）
典型场景 树形结构遍历、分治 普通迭代、大批量计算

限制与相互递归

  • inline 函数不能递归：内联需在编译期展开成有限代码，递归的展开没有终点。
  • 相互递归：A 调 B、B 又调 A；依赖提前声明（呼应 §3），实际用得很少。

实战：用递归改造解析程序

用递归改写字符串解析项目（把按分隔符组织的记录逐条读出）：每次递归只读取一条数据，用指针记录读取位置，每读一条指针后移（++p），查不到分隔符时递归结束。整体代码比「查找-截取」循环更简洁，但要注意控制递归深度、保证结束条件。

警告：递归函数第一要务是结束条件；没有结束条件 = 栈溢出崩溃。递归深度不可控的场景（如处理用户输入、网络数据）要谨慎，必要时改用循环或显式栈。

§9 练习与自查

先独立作答，再对照参考答案。能用自己的话讲清每一条，才算真正掌握。

第 1 题：静态局部变量和普通局部变量在生命周期、作用域、存储位置上有何区别？
生命周期：静态局部变量与全局变量相同、程序结束才销毁，普通局部变量函数结束即销毁；作用域：两者都只在所在函数内可见；存储位置：静态局部变量在全局（静态）存储区，普通局部变量在栈上。

第 2 题：为什么「声明可以有多次，而定义只能有一次」？
声明只提供签名、不分配内存，多次声明不产生冲突；定义会分配内存/产生实体，同一实体出现两份时链接器无法决定用哪一个，因此只能有一次。

第 3 题：头文件里能不能写函数定义？什么情况下可以？
能写，但一般不建议。头文件被多个源文件包含时，普通函数定义会被复制多份导致重定义；static 变量/函数（各自文件独立一份）和 inline 函数是例外。

第 4 题：C++ 工程中调用定义在 .c 文件里的函数报「无法解析的外部符号」，如何解决？
原因是名字修饰不一致：C++ 编译时把函数名修饰成带参数信息的符号，而 .c 文件产生 C 风格符号。用 extern “C” 把声明（或整个头文件）按 C 风格处理即可。

第 5 题（代码）：写出用递归求 n 的阶乘的函数；并说明为什么没有结束条件的递归会导致程序崩溃而不是卡住。

第 6 题：__cdecl 与 __stdcall 有什么区别？为什么 printf 只能是 __cdecl？
参数都从右到左入栈；__cdecl 由调用者恢复栈平衡并支持不定参数，__stdcall 由被调函数恢复栈平衡、不支持不定参数。printf 参数个数不固定，只有调用者知道压了多少参数，所以只能是 __cdecl。

第 7 题：#pragma once 与 #ifndef 保护各自有什么优缺点？
#pragma once 写法简洁、无宏名冲突风险，但是非标准指令，个别编译器不支持；#ifndef 是标准写法、兼容所有编译器，但宏名必须全工程唯一，否则内容会被静默跳过。
