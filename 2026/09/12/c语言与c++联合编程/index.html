静态变量 static

在普通变量声明前加上 static 关键字，就得到一个静态变量。它解决的是「函数结束后，变量还在不在」的问题。

语法

特性

  • 只初始化一次：整个程序运行期间只初始化一次，之后每次进入声明它的函数，都不会再执行初始化语句。
  • 自动初始化为 0：声明时不指定初始值，编译器自动初始化为 0（与普通局部变量「不初始化就是随机值」完全不同）。
  • 生命周期与全局变量相同：程序启动时创建，程序结束时销毁；不因函数返回而消失。
  • 作用域不变：仍是局部变量，只能在声明它的函数内访问；存储位置不在栈上，而是放在全局（静态）存储区。

警告：「只初始化一次」不是「值不变」：每次进入函数仍会执行函数体内其他语句，只是初始化语句不再执行。static 扩大的是生命周期，不是作用域。

内联函数 inline

在函数声明（或定义）前加上 inline 关键字，是告诉编译器：最好把这个函数「内联」处理。它解决的是「小函数调用开销值不值」的问题。

语法

原理

普通函数调用在汇编层面要做：参数压栈（push）、call 跳转、恢复栈帧、返回后恢复栈平衡。内联函数则把函数体代码直接展开到调用处，省掉压栈、出栈和跳转的开销。

适用条件

  • 函数体只有一两行（如 return a + b;）时，入栈/出栈的固定开销占比大，内联收益明显；
  • 函数体几千行时，固定开销可以忽略，内联没有意义。

警告：inline 函数不能递归：递归函数无法在编译期展开成有限代码，编译器不会采纳内联建议（详见 §8 递归函数）。

声明与定义

「声明（declaration）」和「定义（definition）」是 C/C++ 最基础也最容易被忽视的概念。多文件工程里各种「找不到标识符」「重定义」「无法解析的外部符号」错误，根源几乎都在这里。

为什么必须先声明后使用

编译器从第一行往后逐行翻译。遇到 ave(12, 8) 这样的调用时，它必须先知道 ave 的返回类型和参数类型，否则无法生成调用代码，报「找不到标识符」。解决办法就是在调用之前先给出声明。

声明与定义的区别

对比项 声明 declaration 定义 definition
作用对象 编译器 计算机（通过编译器翻译）
内容 签名：返回类型 + 参数类型 签名 + 函数体（实现）
内存分配 不分配 分配
出现次数 可以多次 只能一次
变量写法 extern int a; int a = 25;
函数写法 int ave(int, int); int ave(int a, int b) { ... }

备注：记忆口诀：声明是「我们和编译器之间的事」（为了让编译通过）；定义是「我们通过编译器告诉计算机的事」（真正分配内存、产生机器代码）。函数声明中的参数名可以省略（int ave(int, int); 合法），但写上更利于阅读。

变量的声明与定义：extern

变量默认写法 int a = 25; 或 int a; 都是「定义」——因为要分配内存。只想声明全局变量而不定义，必须使用 extern：

  • 函数默认就是 extern：函数声明即使不写 extern 也按 extern 处理（「声明可多次」正是基于此）；变量不加 extern 时默认视为定义。
  • extern 只作用于全局：函数体内用 extern 声明局部变量会报「重定义」错误。
  • 意义：库作者给别人看头文件时，别人只需看到声明；真正分配内存的定义放在某个源文件中。

程序的内存布局

理解「定义分配内存」的底层含义，需要知道程序的内存长什么样。

  • 4GB 虚拟地址空间：32 位进程默认拥有 2³² = 4GB 虚拟地址空间，与物理内存大小无关；超出实际内存的部分通过「内存交换」换到硬盘，所以内存被撑爆后程序会明显变卡。
  • 地址空间划分：低地址空指针区（0x00000000 附近，访问即崩溃，这是空指针解引用的本质）→ 用户区 → 内核区（0x80000000 以上，操作系统使用）。
  • 用户区四分区：全局变量区（全局变量和 static 变量）、代码区（函数二进制代码）、栈区（局部变量）、堆区（自由存储区，new/malloc 动态分配）。
  • 固定地址：全局变量和函数在编译期分配相对固定地址（加载后只做很小基址偏移）；局部变量每次调用都在栈上动态分配，没有固定地址。

备注：因为全局变量、函数地址相对固定，逆向时很容易被定位（如游戏外挂通过固定地址读写全局数据）；这也提示：不要把数据都放到全局区。

警告：「找不到标识符」＝编译器在调用点之前没见过该函数的声明/定义，不一定是函数不存在；声明写 100 次没事，定义写 2 次必错——这是多文件工程「重定义」错误的总根源。

头文件与源文件

一个人盖不了摩天大楼，所以要分工；一个大型项目有几万个函数，不可能写在一个文件里。模块化就是把代码拆到多个文件，再用头文件把它们「拼接」起来。

源文件与编译流程

  • .cpp 是 C++ 源文件，.c 是 C 源文件；.c 文件要用 C 语法（printf/scanf，需 stdio.h）。
  • 编译器只编译源文件：每个 .cpp 单独编译成目标文件 .obj，最后把所有 .obj 链接成可执行文件 .exe。
  • #include "xxx.h" 的作用，是把 xxx.h 的完整内容复制到当前源文件中再一起编译；头文件本身不会被单独编译。

备注：推论：头文件里写有明显语法错误的代码，只要没有源文件包含它，工程仍能编译通过；一旦某个源文件 #include 了它，编译立刻报错。

实践：把自己的函数组织成「源文件 + 头文件」

头文件里能放定义吗

  • 语法上可以，工程上不行：头文件被复制进每一个包含它的源文件，普通函数定义会被复制多份，链接时报「重定义」。
  • 两个例外：static 变量/函数（内部链接，每个源文件各一份独立内存空间，互不冲突）和 inline 函数（同样允许）。
  • 跨文件共享全局变量：定义只能写一次（放某个源文件），其他源文件用 extern 声明引用；extern 声明不能带初始化值。

防止头文件被重复包含

同一个头文件可能被多个头文件间接包含多次，每个头文件都应加「防止重复包含」保护，两种写法：

对比项 #pragma once #ifndef 宏保护
标准性 非标准指令 C/C++ 标准预处理器指令
写法 一行 三行（#ifndef/#define/#endif）
宏名冲突风险 无 有（宏名需全工程唯一）
支持的编译器 多数现代编译器 所有编译器

警告：两种保护都只对「单个源文件内的重复包含」有效，不是「整个工程只编译一次」——不同源文件包含同一头文件，各自仍展开一份，所以头文件里依然不能放普通函数定义。#ifndef 的宏名若与其他头文件撞名，后包含的内容会被整个跳过，报「找不到标识符」。

条件编译：#if / #ifdef / #ifndef

#ifdef：定义了宏就编译其中的代码；#ifndef：没定义才编译。它们在编译期起作用——不满足条件的代码，编译器根本不会编译。

提示：典型应用是版本管理：同一份源码通过是否定义宏，编译出「VIP 版」和「普通版」两份程序，未定义宏对应的代码不会进入可执行文件，产物大小也会明显不同。另注意：#include 尖括号与双引号查找路径不同——尖括号在编译器的包含目录中查找，双引号优先在当前目录查找。

C 与 C++ 混用：extern “C”

大型项目里可能既有老的 C 风格代码，又有新的 C++ 代码。但 C 和 C++ 对函数名的处理方式不同，直接混用会链接失败。

问题的根源：名字修饰

  • C++：函数名被修饰。C++ 支持重载，编译器编译时把函数名「修饰」成带参数信息的符号（如 ?ave@@YAHHH@Z 这类乱码式符号名）。
  • C：函数名保持原样。C 不支持重载，编译后的符号就是函数名本身（如下划线 + 函数名 _ave）。
  • 症状：C++ 源文件调用定义在 .c 文件中的函数时，C++ 按修饰后符号去找，而 .c 产生的是未修饰符号，两头对不上 → 「无法解析的外部符号」。

警告：extern "C" 只解决「C++ 调用 C 函数」的方向；反过来，.c 文件无法调用 C++ 函数（C 编译器不认识 C++ 修饰符号），只能把 C++ 函数声明成 C 风格来迁就。且被 extern "C" 包裹的函数不支持重载——重载依赖名字修饰，C 风格函数不修饰名字。

静态库与项目模板

用过的 printf、STL 都来自别人封装好的库。这一节把前面的知识串起来：自己做函数 → 打包成静态库 → 配置给其他人用 → 把工程导出成项目模板。

什么是库 / SDK

库就是「实现 + 声明」的打包：把函数实现编译成 .lib（静态库）文件，头文件作为说明书一起发布。把库、文档、示例程序打包发布，就构成 SDK。版本号等常量应在头文件开头用 const 常量定义，并可以把函数、变量、常量装进自己的命名空间（模仿 std），避免与使用者的名字冲突。

制作静态库的步骤

2 写声明 新建头文件 MyLib.h，放全部函数声明 函数声明（说明书）
3 改配置 工程属性 → 常规 → 配置类型 → 静态库(.lib) 不再生成 .exe

使用静态库的三步配置

  1. 包含目录：把头文件所在目录加入「VC++ 目录 → 包含目录」（对应 #include <xxx.h> 尖括号查找路径）。
  2. 库目录：把 .lib 所在目录加入「VC++ 目录 → 库目录」。
  3. 指定链接的库：代码里写 #pragma comment(lib, "MyLib.lib")；或在工程属性 → 链接器 → 输入 → 附加依赖项中填写库名（多个库用分号分隔）。

备注：记忆：包含目录让编译器找到「声明」，库目录 + 链接器配置让链接器找到「实现」。缺一步分别报「找不到头文件」或「无法解析的外部符号」。

  • 用途：把配置好依赖（包含目录、库目录、链接器设置）的工程导出成模板，以后新建项目选这个模板，环境自动配好。
  • 导出：项目 → 导出模板 → 项目模板 → 填写模板名称 → 勾选「自动导入」。生成一个与模板同名的 .zip 文件。

提示：典型应用：游戏引擎基础工程（俄罗斯方块、贪吃蛇共用的配置与基础代码）、SDK 发布——用户创建项目即自带全部环境。#pragma comment(lib, ...) 是 MSVC 专有写法，跨编译器工程用「链接器附加依赖项」或构建脚本更通用。

函数调用约定

函数调用在机器层面要解决两件事：参数怎么传递、栈平衡由谁来恢复。调用者与被调用函数之间关于这两件事的「协议」，就是调用约定。

背景

参数通过栈传递（默认从右到左压栈），压栈破坏了栈平衡，函数返回后必须恢复（普通函数调用后常见 add esp, 8 之类的指令）。约定不同，参数传递方式、栈平衡恢复方、编译后的符号都不同。x86（32 位）下常见三种：

__cdecl（默认约定）

  • 参数从右到左入栈；栈平衡由调用者恢复（谁调用谁负责清理）。
  • 因为调用者知道自己压了几个参数，支持不定参数——printf 就是典型的 __cdecl 函数。
  • 默认不写就是它。

__stdcall

  • 参数从右到左入栈；栈平衡由被调函数自己恢复（函数内部用 ret n 清理）。
  • 被调函数不知道调用者压了几个参数，不支持不定参数。
  • 符号名形如 _函数名@参数总字节数（如 _add@8）；Win32 API 大量使用。

__fastcall

  • 前两个参数通过寄存器传递（依次放入 ECX、EDX），其余参数仍压栈；寄存器在 CPU 内部，比访问内存快。
  • 剩余参数的栈平衡由被调函数恢复。
  • x86 下默认是 __cdecl；x64 架构下默认约定相当于 fastcall 家族（细节不同）。

备注：naked：不生成编译器自动添加的序言/尾声代码，几乎不用，只在驱动开发等特殊场景出现。

栈平衡恢复方 调用者 被调函数 被调函数

警告：看到「无法解析的外部符号」时，除了查名字修饰，还要注意调用约定不一致（如一边 __cdecl 一边 __stdcall）也会导致符号对不上。不定参数函数只能是 __cdecl；寄存器传参只对前两个参数有效，参数更多时依然走栈。

递归函数

递归函数是在函数体内调用它自己的函数——像蛇咬住自己的尾巴。它并不特殊，只是多了一个「不该做的操作」：调用自身。

定义与退出机制

递归函数是「自己控制退出」的循环，必须设计好结束条件；没有结束条件的递归会变成死递归，最终导致程序崩溃。

示例：用递归求 1 到 x 的和

执行过程：sum(10) = 10 + sum(9) = 10 + 9 + sum(8) = … 一路展开到 sum(1) = 1，再逐层回代，最终得到 55。

栈溢出：为什么死递归会崩溃

  • 函数每一次调用都会创建栈帧（压栈、传参）。递归每深入一层就压一个栈帧，直到把栈空间耗尽——栈溢出，程序直接崩溃。
  • 循环卡住只是程序不响应；多线程中最多卡住一条线程。递归一旦失控是必然的栈溢出崩溃，且影响整个进程。
  • 递归每层都有函数调用开销（压栈、传参、恢复栈平衡），执行效率低于等价循环；但代码量少、逻辑清晰，可读性强。
对比项 递归 循环
代码量 少、简洁 相对多
可读性 结构清晰（尤其树形问题） 一般
执行效率 低（每次调用压栈传参） 高
失控后果 栈溢出、程序崩溃 卡住（单线程）
典型场景 树形结构遍历、分治 普通迭代、大批量计算

限制与相互递归

  • inline 函数不能递归：内联需在编译期展开成有限代码，递归的展开没有终点。
  • 相互递归：A 调 B、B 又调 A；依赖提前声明（呼应 §3），实际用得很少。

实战：用递归改造解析程序

用递归改写字符串解析项目（把按分隔符组织的记录逐条读出）：每次递归只读取一条数据，用指针记录读取位置，每读一条指针后移（++p），查不到分隔符时递归结束。整体代码比「查找-截取」循环更简洁，但要注意控制递归深度、保证结束条件。

警告：递归函数第一要务是结束条件；没有结束条件 = 栈溢出崩溃。递归深度不可控的场景（如处理用户输入、网络数据）要谨慎，必要时改用循环或显式栈。

练习与自查

第 1 题：静态局部变量和普通局部变量在生命周期、作用域、存储位置上有何区别？
生命周期：静态局部变量与全局变量相同、程序结束才销毁，普通局部变量函数结束即销毁；作用域：两者都只在所在函数内可见；存储位置：静态局部变量在全局（静态）存储区，普通局部变量在栈上。

第 2 题：为什么「声明可以有多次，而定义只能有一次」？
声明只提供签名、不分配内存，多次声明不产生冲突；定义会分配内存/产生实体，同一实体出现两份时链接器无法决定用哪一个，因此只能有一次。

第 3 题：头文件里能不能写函数定义？什么情况下可以？
能写，但一般不建议。头文件被多个源文件包含时，普通函数定义会被复制多份导致重定义；static 变量/函数（各自文件独立一份）和 inline 函数是例外。

第 4 题：C++ 工程中调用定义在 .c 文件里的函数报「无法解析的外部符号」，如何解决？
原因是名字修饰不一致：C++ 编译时把函数名修饰成带参数信息的符号，而 .c 文件产生 C 风格符号。用 extern “C” 把声明（或整个头文件）按 C 风格处理即可。

第 5 题（代码）：写出用递归求 n 的阶乘的函数；并说明为什么没有结束条件的递归会导致程序崩溃而不是卡住。

第 6 题：__cdecl 与 __stdcall 有什么区别？为什么 printf 只能是 __cdecl？
参数都从右到左入栈；__cdecl 由调用者恢复栈平衡并支持不定参数，__stdcall 由被调函数恢复栈平衡、不支持不定参数。printf 参数个数不固定，只有调用者知道压了多少参数，所以只能是 __cdecl。

第 7 题：#pragma once 与 #ifndef 保护各自有什么优缺点？
#pragma once 写法简洁、无宏名冲突风险，但是非标准指令，个别编译器不支持；#ifndef 是标准写法、兼容所有编译器，但宏名必须全工程唯一，否则内容会被静默跳过。

编译与链接：翻译单元

写代码只是第一步，真正把代码变成程序的是编译器。你可以把编译器想象成「翻译官」：我们写的是给编译器看的源码，编译器把它翻译成机器能执行的机器码。这一节解决的是「源码到底经历了什么才变成 .exe」。

翻译单元（Translation Unit）

每个 .cpp 源文件在编译时，会先把 #include 的头文件完整复制进来（#include 的字面意思就是「包含」），合并后的整体就是一个翻译单元（也叫编译单元）。它是编译器处理的最小独立单位。

编译与链接两步流水线

  • 编译：把每个翻译单元单独编译成目标文件 .obj。目标文件里是翻译好的机器码，以及一张「引用信息表」（本单元用到了哪些还没找到地址的名字）。
  • 链接：链接器把多个 .obj 拼起来：如果 A 单元调用了定义在 B 单元的函数，链接器就负责在 B 的机器码里找到这个函数，把地址填回去，最终生成 .exe（或 .lib、.dll）。
对比项 编译（Compile） 链接（Link）
输入 翻译单元（.cpp + 头文件） 目标文件 .obj
输出 .obj 目标文件 .exe / .lib / .dll
职责 逐行翻译成机器码 解析引用、拼接地址
错误码特征 C 开头（如 C2080） LNK 开头（如 LNK2019）

警告：看到报错先认「阶段」：C2080 这类 C 开头错误发生在编译期（某个翻译单元内部的问题）；LNK2019 无法解析的外部符号 这类 LNK 开头错误发生在链接期——语法没错，但链接器找不到引用函数的定义（比如声明了 extern 函数却没在任何 .cpp 里实现它）。

未定义行为（Undefined Behavior）

C++ 标准委员会规定了语言的「标准行为」，但标准并没有规定所有情况。当代码落在标准没规定的行为上时，结果完全取决于编译器心情——这就是未定义行为（UB）。

典型例子：同一表达式中变量既自增又被读取

这不是运算符优先级问题（优先级只决定「谁先算」的次序），而是「同一个表达式里先读 a 还是先改 a」的求值顺序没有被标准规定。不同编译器、甚至同一编译器不同版本，结果都可能不同。

常见的未定义行为

  • 同一表达式中对同一变量既读又写（如 ++a + a）；
  • 有符号整数溢出（如 int 加到超过上限）；
  • 除零、空指针解引用、越界访问数组。

备注：未定义行为难以靠编译器查出来（编译器甚至不检查），所以写代码时要有意识地避开。能避免就避免，遇到多了解。标准委员会「没规定」≠「没毛病」，只是把责任留给了程序员。

警告：为什么老师的经验是「不要写 ++a + a 这种代码」？因为它在不同编译器上表现不同——这不是编译器坏了，而是你踩进了未定义行为的区域。

单一定义规则 ODR 与链接属性

多文件工程最常见的两类报错：「重定义」（defined multiple times）和「无法解析的外部符号」（unresolved external symbol）。它们的理论根源都来自同一个规则——ODR（One Definition Rule，单一定义规则）。

ODR 的核心规定

  • 变量、函数、类、枚举、模板：在每个翻译单元中只能有一个定义，但可以有多个声明；
  • 非内联的函数或变量：在整个程序中有且仅有一个定义。

声明写 100 次都没事（只是告诉编译器「长什么样」）；定义写 2 次必错（编译器/链接器不知道用哪一份）。

ODR 的例外：可以放多个「定义」的东西

  • const 常量（默认内部链接，每个翻译单元各一份，互不冲突）；
  • static 变量 / 函数（内部链接）；
  • inline 函数 / 变量（C++17 起，外部链接但允许重复定义、多份合并为一份）；
  • 类内定义的成员函数、模板（天然允许多个翻译单元各有一份，链接时合并）。

备注：ODR 非常复杂，标准文档有几十页。本课只掌握两句话：①「声明可多次、定义只能一次」；②「想打破这个限制，用 const / static / inline」。

链接属性：内部链接与外部链接

链接器靠名字连接各目标文件，所以每个名字都必须有唯一的「身份」——这就是链接属性（Linkage）。C/C++ 的链接属性分三种：

链接属性 含义 典型对象
无链接 仅在其作用域（代码块）内有效 函数内的普通局部变量
内部链接 仅在本翻译单元内有效，其他文件访问不到 static 变量/函数、const 常量
外部链接 在整个程序中有效，其他翻译单元可引用 全局变量、普通函数、extern 声明
  • static：把名字从外部链接「降级」为内部链接——只在当前 .cpp 里有效，其他文件即使声明了 extern 也找不到它。早期代码常用 static 隐藏实现细节，但现在标准委员会不推荐用 static 函数做隐藏（推荐用匿名命名空间，见 §7）。
  • const：全局 const 默认也是内部链接（每个 .cpp 各有一份独立副本），所以两个文件里都写 const int VERSION = 1; 不会冲突；加上 extern 才转为外部链接：extern const int VERSION;。
  • extern：声明「这个名字在别的翻译单元里有定义」，让本单元引用外部定义的名字。

inline 变量（C++17）

普通全局变量定义只能写一次（放某个 .cpp 里），头文件里放定义就会「重定义」。inline 变量是 C++17 的新特性：允许在头文件里定义变量，多个翻译单元包含它也不会报重定义——链接器会把所有副本合并成同一个实体。

  • inline 变量具有外部链接属性，但允许重复定义（ODR 例外）；
  • static 变量是内部链接，每个翻译单元各一份独立内存——两者本质不同；
  • 普通（非 inline）变量定义在头文件里仍是重定义错误，必须配 C++17 标准。

警告：记忆要点：inline 保留外部链接且多份合一；static 是内部链接各管各的。前者适合「头文件里放全局常量/配置」，后者适合「本文件私用」。inline 变量写函数早已支持，写成变量是 C++17 才支持的，注意别把语法混了。

宏定义 #define

所有以 # 开头的行，都是预处理指令——它们是「和编译器对话」的指令，不会编译进最终代码，而是在编译开始前由预处理器做纯文本替换。

对象式宏：定义常量与提升可读性

  • 好处：一处定义、多处使用；改版本号只需改一行；用有含义的名字（SCREEN_WIDTH）提升可读性。

  • 宏名规则：像变量名——字母、数字、下划线、中文都可以，但不能以数字开头。

  • 无值宏：#define FLAG（后面不跟内容）等价于「把 FLAG 定义为空」，专门用来当标识开关，配合 §5 条件编译 使用。

  • 不替换的情况：出现在注释里、或已经是某个更长标识符的一部分时（如 MY_FLAG2 中的 MY_FLAG）不会替换。

    函数式宏：带参数的宏

  • 宏的「参数」只是文本替换：调用处被原样展开，没有函数调用的压栈/跳转开销，也没有类型检查；
  • 参数和整体都要加括号：MAX(a + 1, b) 若写成 a > b ? a : b 展开后运算顺序会出错；
  • 它只是「长得像函数」，不是函数，不能递归，没有作用域。

提示：经典实用宏：申请并释放内存的固定组合 free(p); p = NULL; 可以打包成一个宏，减少重复代码。但复杂的宏会让代码难调试，现代 C++ 更推荐用 const 常量、inline 函数、模板替代宏。

字符串化 与 ## 连接

  • # 把参数转成字符串字面量，自动处理转义，无需手写双引号；

  • ## 把两个记号拼接成一个新记号（常用于批量生成名字）。

    #undef：取消宏定义

备注：宏的生效/失效顺序按代码书写顺序（从上往下预处理），不是函数执行顺序。#undef 后宏立即失效。

「只在本翻译单元内有效」的需求，标准委员会现在推荐用匿名命名空间，而不是 static 函数：

  • 匿名命名空间内的名字具有内部链接属性，只在当前翻译单元有效；
  • 它不参与命名空间「扩展合并」——不同翻译单元里的匿名命名空间是各自独立的；
  • 兼容性原因，static 写法仍可用，但新代码推荐匿名命名空间。

程序越大、逻辑越复杂，越难免出 bug。写 Hello World 不会出错，不代表能力问题——排错能力才是工程能力的一部分。

错误的两种类型

对比项 语法错误（编译错误） 逻辑错误（运行错误）
发现时机 编译期，编译器直接报错 运行期，程序能编译通过
典型例子 变量名以数字开头、使用未初始化的内存 计算学生成绩时排错位（结果不符合预期）
排查难度 易，双击错误信息跳到出错行 难，需要调试器跟踪变量

写代码的四个好习惯（让排错更容易）

  • 模块化：能写成函数就写成函数，独立功能独立封装，别一写几十行堆在一起；

  • 命名直观：函数名/变量名/类名/结构体名要让人一眼看懂用途，最好不用看注释；

  • 正确缩进与断行：if/else 配对的缩进一致，逻辑结构一眼可见；

  • 写注释：方便日后排错和理解（老师自嘲自己写代码不爱写注释是反面教材）。

    调试器核心操作（VS 自带调试器）

  • 断点：在语句左侧点红点，程序执行到这里就停下；可以下多个断点，运行中也可以随时补；

  • 继续：从断点处恢复运行到下一个断点；

  • 逐语句（Step Into）：一句一句执行；遇到函数调用会进入函数内部看实现；

  • 逐过程（Step Over）：不进入函数内部，直接执行完整个函数调用（但函数确实执行了）；

  • 跳出（Step Out）：在函数内部想直接返回上一层，点它立即退出当前函数；

  • 观察窗口 / 局部变量窗口：实时查看变量的当前值——定位「哪个变量在什么时候变成了意外值」是调试的核心；

  • 寄存器窗口：查看 EAX/EBX/ECX/EDX 等 CPU 寄存器，配合反汇编使用（写普通代码很少用）；

  • 反汇编窗口：按汇编指令逐条执行，适合底层研究（高端局才用）。

备注：调试的核心思路：先怀疑某个变量的值，下断点 → 逐语句跟踪 → 在观察窗口看它每一步的变化 → 找到「第一次变成错误值」的那一行，错误根源就定位了。比如结果每隔几个学生就错一位，往往是「计数器没有在每个班级开始处清零」。

其他调试器

  • OllyDbg（OD）：著名的逆向调试器，本身就是一个调试器；正常写代码用 VS 即可，需要深入反汇编时才用它；

  • x64dbg：较新的调试器，以后课程会涉及；

  • WinDbg：较老、偏底层，常配合双机调试（电脑 A 调试电脑 B）使用。

断言 assert 与 static_assert

「断言」翻译自英文 assert——用一句断言声明「这里必须是这个条件」，条件不成立就立刻暴露问题。它专门用来捕捉那些你很重视、但又不确定会不会发生的情况（空指针、野指针、非法输入等）。

运行时断言：assert 宏

  • 语法：assert(布尔表达式)。任意数值都会转成 bool：非 0 为真、0 为假；
  • 表达式为 false 时，程序弹出错误信息（含文件名、行号、表达式），可选择终止 / 重试 / 忽略；
  • 只用于调试期显式找错，不要用它处理用户输入校验（正式程序里应该用 if 处理非法输入）。

用 NDEBUG 关闭 assert

警告：NDEBUG 必须在包含 <cassert> 之前定义才有效——头文件被合并进源文件时，assert 是否启用就已经由当时的宏状态决定了。它的原理是 #ifdef NDEBUG 让 assert 展开为空操作。

编译期断言：static_assert

assert 是运行时检查（程序跑起来才知道）；static_assert 是编译期检查（编译阶段就能验证），且不需要任何头文件，条件必须是常量表达式：

  • 条件为假 → 编译失败，输出你写的错误信息；
  • 因为发生在编译期，条件里不能是运行时的变量值；
  • 典型应用：平台/位数校验——例如强制程序只在 32 位下编译：
对比项 assert static_assert
检查时机 运行时（程序执行到该行） 编译期
头文件 需要 不需要
条件要求 任意表达式（转 bool） 必须是常量表达式
失败后果 弹出错误对话框 编译失败并输出信息
典型用途 空指针/野指针等运行时可疑点 平台位数、类型大小、编译期约束

备注：assert 的实现机理：底层调用 CRT 的诊断函数，弹出带文件名、行号的对话框——这些都是编译器底层提供的。有兴趣完全可以自己实现一个「自定义断言宏」；日常使用记住「NDEBUG 关 assert、static_assert 管编译期」就够了。

练习与自查

先独立作答，再对照参考答案。能用自己的话讲清每一条，才算真正掌握。

第 1 题：什么是翻译单元？编译和链接分别做什么？
一个 .cpp 源文件把 #include 的头文件内容复制进来后形成的整体叫翻译单元。编译：把翻译单元翻译成 .obj 目标文件（机器码 + 引用信息）；链接：把多个 .obj 的引用解析到实际地址，拼成 .exe / .lib / .dll。

第 2 题：什么是未定义行为？举一个例子并说明为什么不同编译器结果不同。
标准没有规定结果的代码行为就是未定义行为。例：int r = ++a + a; ——同一个表达式里变量既被修改又被读取，求值顺序标准没规定，所以不同编译器可以给出不同结果。它不是运算符优先级问题。

第 3 题：ODR（单一定义规则）的核心内容是什么？哪些情况可以有「多个定义」？
变量/函数/类/枚举/模板在每个翻译单元中只能有一个定义，可以有多个声明；非内联的函数或变量在整个程序中只能有一个定义。例外：const 常量、static 变量/函数（内部链接，各文件独立）、inline 函数/变量（C++17）、类内定义和模板。

第 4 题：static、const、extern、inline 变量各自的链接属性是什么？
static：内部链接，仅本翻译单元有效；const：全局 const 默认内部链接，加 extern 变外部链接；extern：声明外部定义的名字（外部链接）；inline 变量（C++17）：外部链接但允许重复定义，头文件里定义多份链接时合并成一份。

第 5 题：#define 与 const 有什么区别？函数式宏为什么要给参数加括号？
#define 是预处理期纯文本替换，没有类型、没有类型检查，C 风格；const 是真正的变量，有类型、编译期检查严格，C++ 更推荐。函数式宏只是文本替换，不加括号时展开后运算优先级会出错（如 MAX(a+1,b) 展开成 a+1 > b ? a+1 : b），所以参数和整体都要加括号。

第 6 题：#ifdef/#ifndef 和 #if/#elif/#else 分别用于什么场景？
#ifdef/#ifndef 用于判断「某个宏是否定义」，最典型的是头文件防重复包含（#ifndef MYLIB_H / #define / #endif）和功能开关；#if/#elif/#else 用于判断「宏的取值」，典型是版本号控制——同一个版本号宏选不同版本的函数实现，还可以用 && 和 || 组合多个条件。

第 7 题：_DEBUG 宏是干什么的？它如何做到「发布版自动去掉调试输出」？
_DEBUG 是 MSVC 在 Debug 配置下自动定义的预定义宏，Release 配置不定义。用 #ifdef _DEBUG 包住调试输出代码，Debug 版会编译进去，Release 版预处理后这段代码根本不存在，无需手动删代码。

第 8 题：逐语句、逐过程、跳出分别是什么意思？调试逻辑错误的核心思路是什么？
逐语句：一句一句执行，遇函数调用进入函数内部；逐过程：执行完整个函数调用但不进入内部；跳出：在函数内部直接返回上一层。核心思路：怀疑某个变量的值 → 下断点 → 逐语句跟踪 → 在观察窗口看它每一步的变化 → 找到第一次变成错误值的那一行，就定位了错误根源。

第 9 题：assert 和 static_assert 有什么区别？NDEBUG 为什么要写在 #include 之前？
assert 是运行时检查（条件为假弹错误框），static_assert 是编译期检查（条件必须是常量表达式，失败则编译报错，且不需要头文件）。NDEBUG 必须在包含 cassert 之前定义，因为 assert 是否启用由头文件合并时的宏状态决定——预处理阶段 #ifdef NDEBUG 已经把 assert 展开成空操作了。

面向对象编程思想与 class 初识

什么是面向对象编程（OOP）

  • OOP 是一种编程思想：把程序中的一切事物抽象成”对象”，对象拥有属性（数据）和行为（函数），程序通过对象之间的交互完成逻辑。
  • OOP 不是某门语言的专属能力：C 语言也能模拟 OOP（只是实现麻烦）；C++ 原生支持；Java 是纯面向对象语言。
  • 相关概念：OOA（面向对象分析）、OOD（面向对象设计）、SOLID 原则（单一职责、开闭、里氏替换、接口隔离、依赖倒置）——本课只作背景了解。

历史背景（简要）

  • 上世纪 50 年代萌芽，90 年代随硬件发展、软件规模变大成为主流。
  • C 语言面向过程；C++ 在 C 的基础上加入面向对象支持。

面向过程 vs 面向对象（游戏”打人”例子）

OOP 三大特性

特性 含义 本课例子

多态 同一对象在不同场景呈现不同形态 统一按基类 NPC 处理 NPC / Monster / Role，减少重复函数

class 的定义与访问控制

struct 与 class 的区别

  • 默认访问权限：struct 默认 public，class 默认 private。
  • 二者本质相同（都是自定义数据类型，都可以放函数）。
  • 推荐约定：只放数据的纯数据结构用 struct；有封装、有行为的用 class。

成员函数与成员变量

类的两个要素

  • 成员变量 = 属性（数据）；成员函数 = 方法（行为）。

    访问权限与封装

  • public：对外公开；private：对外隐藏（只允许本类内部访问）。

  • private 不表示”不存在”，只是”不给你看”——类似人的内脏不会掏出来给别人看。

    作用域

  • 成员的作用域是类本身：类外不能直接访问，只能通过对象（实例）访问：obj.func() / obj.member。

  • 在类外定义成员函数必须用 类名::函数名 限定作用域，且类内必须先有声明。

声明与定义分离（.h + .cpp）

关联 ODR（一个定义原则）：声明可以有很多次（每个用到它的 .cpp 都 include 头文件），但定义只能有一次；类内直接定义的函数隐式 inline，可安全放进头文件被多个文件共享。

类的大小

  • 对象大小只由成员变量决定；成员函数不占对象空间（函数代码在所有对象间共享）。

inline 成员函数

  • 短小、频繁调用的函数（如 getter）用 inline 修饰，编译器在调用处就地展开代码，减少调用开销。
  • 推荐写在头文件里（展开代码需要看到完整定义）。
  • 类内直接定义的成员函数天生就是 inline。

this 指针与链式调用

  • 每个成员函数里都有一个隐藏的 this 指针，指向”当前调用该函数的对象”。
  • this->hp 与直接写 hp 等价。
  • 返回 *this 的引用可实现链式调用，且避免拷贝：

const 成员函数

const 对象

  • const 修饰的对象：内存空间不可变，成员变量不能被修改。
  • 注意区分：通过 const Node* p 不能修改所指内容，是因为指针的类型是”指向 const”，而不是因为目标对象本身是 const。

const 成员函数语法

  • const 写在括号后面表示”该函数不修改成员”；写在括号前面只是修饰返回值。

规则：const 对象只能调用 const 成员函数

const 成员函数内部的 this

  • const 成员函数中 this 自动变成 const Node*，因此：
    • 不能修改成员变量；
    • 不能调用非 const 成员函数；
    • 不能返回指向成员的非 const 引用/指针（否则外部可以绕过 const 修改）。

构造函数（入门）

什么是构造函数

  • 特殊成员函数：对象创建时自动调用，不需要手动调用。
  • 特点：名字与类同名；没有返回值（void 也不行）；用于初始化成员变量。

构造函数的重载

  • 构造函数可以有多个（参数不同），调用时按参数匹配——本质是函数重载。

默认构造函数

  • 只要定义了任意构造函数，默认构造函数就不再生成了（除非显式要求）。

    拷贝构造函数

  • 触发时机：User b(a); 或 User b = a;（对象尚未构造时）。

析构函数

什么是析构函数

  • 特殊成员函数，对象销毁时自动调用（离开作用域、生命周期结束的瞬间）。
  • 与构造函数是一对”兄弟”：构造负责初始化，析构负责收尾/销毁。

语法与特点

  • 写法：~类名()，无参数、无返回值。
  • 不能重载（没有参数、无法区分），一个类只能有一个析构函数。
  • 不写时编译器自动生成一个空的析构函数。

关键坑点

  1. 不能直接指向字面量：data_ = "你好" 会让析构函数对字符串字面量执行 delete → 崩溃。必须 new + 拷贝。
  2. 浅拷贝导致 double free：用默认拷贝构造函数，两个对象的 data_ 指向同一块内存，析构时都 delete → 第二次 delete 出错。必须自定义深拷贝。

优化思路

  • set 时不要无脑 delete 再 new：先判断已有容量是否够用，够则直接复用。
  • 同时记录”字符长度”与”内存容量”两个值，避免重复 strlen。

高频易错点清单

  1. 构造函数无返回值，也不能写 void。
  2. 拷贝构造函数参数必须是引用，否则无限递归（栈溢出）。
  3. 成员初始化列表按成员声明顺序执行，不按书写顺序。
  4. 空类 sizeof 为 1，不是 0。
  5. const 对象只能调用 const 成员函数。
  6. 默认拷贝是浅拷贝，含动态内存的类必须自己写深拷贝，否则 double free。
  7. 自定义构造函数后，默认构造函数不再自动生成，需要时写 = default。
  8. 析构函数无参数、无返回值、不能重载。
  9. 类内定义的成员函数隐式 inline；inline 成员函数推荐放头文件（与 ODR 相关）。
  10. 同一类的不同对象之间可以互访私有成员。

静态成员变量

复习：static 关键字

  • 函数内的 static 局部变量：终生只定义（分配内存）一次，函数执行多少次都不会重新分配；生命周期与整个程序一样长（类似全局变量）。
  • static 的链接属性：内部链接（只在本翻译单元可见）。
  • 现代 C++ 不推荐用 static 做内部链接，改用匿名命名空间（unnamed namespace）。

静态成员变量的语法

三个核心特点

特点一：所有实例共享同一份静态成员变量

特点二：没有实例也能访问

普通成员必须 对象.成员 才能访问，静态成员用 类名::成员 或 对象.成员 都行。

特点三：静态成员变量”不完全属于类”

  • 属于类的部分：作用域（必须 T::count，不能单独写 count）。
  • 不属于类的部分：内存空间不随对象分配，也不占对象大小。
  • 本质：静态成员变量就是一个全局变量（程序一开始就分配内存，地址固定），编译器只是额外限制了它的作用域（只能用类名访问）和访问权限。

为什么有这些限制（逻辑解释）

  • 非静态成员变量在实例化时才分配内存；静态成员函数在没有实例时也能调用，此时非静态成员根本不存在，自然无法访问。
  • const 修饰的作用是限定 this 指向的对象不被修改；静态函数没有 this，所以 const 无意义。
  • this 指向”当前调用函数的那个对象”，没有对象就没有 this。

底层本质（01.25.7 会展开）：静态成员函数在汇编层面就是一个普通函数，根本不接收 this 指针；访问成员变量全靠 this + 偏移，没有 this 就无从访问。

友元（friend）

概念

  • 封装（private）的目的：隐藏不想给外人看的东西。
  • 但某些场景确实需要”外人”访问私有成员 → 类主动声明：”你是我的朋友“，朋友就能访问。
  • 关键字：friend（朋友）。

友元函数

要点：

  • 友元声明放在 public 还是 private 区没有区别。
  • 友元函数不是类的成员函数：它只是被类”单方面认可”，不拥有 this、不属于该类。
  • 一个类可以有多个友元。

友元类

关键特性（易错）

  1. 单方向：T 说”Helper 是我的朋友”→ Helper 能访问 T 的私有；但 T 不能因此访问 Helper 的私有（除非 Helper 也声明 T 是朋友）。就像”你把对方当朋友，对方不一定把你当朋友”。
  2. 身份独立：友元不是成员的”包含关系”，T 并不拥有 Helper。
  3. 破坏封装：乱交朋友会让 private 形同虚设；只有在没有更好选择时才用。

补充：前向声明

  • 当 friend 声明中用到尚未定义的类（例如函数参数类型），编译器还不认识它，需要提前写 class T1; 前向声明。

嵌套类

概念

  • 嵌套类：把类写进另一个类里面（内层类）。
  • 外层类 / 外围类：包含嵌套类的类。
  • 作用：当某个类（如武器 Weapon）只有外层类（如角色 Role）使用、别处用不到时，写进去层次结构更清晰。

作用域问题

  • 嵌套类的作用域是外层类：外部不能直接 Weapon w;，必须 Role::Weapon w;。
  • 嵌套类声明在 public 区 → 外部可通过 Role::Weapon 使用；声明在 private 区 → 外部无法访问。

在类外定义嵌套类及其成员函数

  • 不带 Role:: 写 class Weapon 会重新定义一个全新的类，不是同一个东西。

不完整类型问题

  • 如果嵌套类只在类内声明、完整定义放到类外，那么外层类不能声明该类型的值成员变量：
  • 解决：把完整定义放回类内；或成员改用指针/引用（指针可以指向不完整类型）。

访问权限（最容易混淆的点）

  • 嵌套类 → 外层类：可以访问外层类的静态成员（包括私有），实例化后也可以访问外层类对象的私有成员（类似友元）。
  • 外层类 → 嵌套类：不能访问嵌套类的私有成员。

一句话：嵌套类比外层类”权限大”，像单向友元；别以为”Weapon 是 Role 的一部分，Role 就能随便访问 Weapon 的私有”——恰恰相反。

局部类（补充知识）

  • 局部类：定义在函数内部的类，作用域仅限该函数。
  • 特点：
    1. 成员函数必须全部定义在类内（函数不能嵌套，无法在类外定义局部类的成员函数）；
    2. 不能有静态成员变量；
    3. 可以访问全局变量；不能访问外层函数的普通局部变量（各编译器行为有差异，标准不保证）；
    4. 尽量少用。

嵌套类的模块化问题

场景

把嵌套类拆到头文件时，最容易踩”互相 include”的坑。

报错现象

  • 编译报：”不允许使用不完整的类型” / “不是类或未定义的类型” 等。

原因：头文件展开顺序（先有鸡还是先有蛋）

  • 假设先 include skill.h → skill.h 又 include role.h → role.h 里 class Role 还没定义完，回到 skill.h 时出现 Role::Skill → 此时编译器还不认识 Role → 报错。
  • 本质：把多个头文件”拼在一起”看展开顺序，Role::Skill 必须出现在 class Role 定义之后。

解决

  1. skill.h 不要 include role.h：如果 Skill 的定义不依赖 Role 的完整定义，这一句完全多余，删掉即可。
  2. 使用方保证先 include 声明了 Role 的头文件，再 include skill.h。
  3. 每个头文件都加 #pragma once（或 include guard）防重复展开。
  4. 更省心的做法：嵌套类直接在类内完整定义，避免跨文件定义。

malloc 与 new 的本质区别

三对关键对比

对比 基本类型（int/float/double…） 类（有构造/析构）
malloc vs new 没有区别 malloc 只分配内存，不调用构造函数；new 分配内存 + 调用构造函数
free vs delete 没有区别 free 只释放内存，不调用析构函数；delete 释放内存 + 调用析构函数
delete vs delete[] 没有区别 delete 只调用第 1 个元素的析构；delete[] 调用每个元素的析构

结论

  • 对类对象：只能用 new / delete（new[] 配 delete[]），不能用 malloc/free。
  • 配对规则：malloc ↔ free、new ↔ delete、new[] ↔ delete[]，不能混用。

为什么静态成员函数没有 this、不能访问非静态成员（底层解释）

  • 调用静态成员函数的汇编没有 ECX 传址这一步，跟调用普通函数一模一样：
  • 没有 this → 无法计算 this + 偏移 → 无法访问非静态成员变量。
  • 所以：静态成员函数本质 = 普通函数（只是名字归属于类）；静态成员变量本质 = 全局变量（固定地址直接寻址，汇编里 mov eax, [count的固定地址]）。

类一定有构造函数吗？（逆向视角）

  • 标准层面：每个类至少有一个构造函数（没写则编译器补默认构造）。
  • 但编译器会删除无意义的空构造：如果成员不需要任何初始化，反汇编里根本看不到构造函数（调用处也没有任何调用）。
  • 一旦成员有类内初始化（如 int hp = 3500;），编译器就会生成默认构造函数去完成赋值，反汇编里就能看到。
  • 注意：要在 Release + 关闭优化 下观察，优化开太大函数会被优化掉。

对逆向/面试的意义

  • 看到 lea ecx, [对象地址] → 基本可以断定：这是一个类的成员函数调用，ECX 里就是 this。
  • 通过 this 指针 + 偏移就能拿到对象的所有数据（血量、坐标、属性…）。
  • 面试高频题：”为什么静态成员函数不能访问非静态成员变量？” 答：访问成员变量依赖 this 指针 + 偏移，而静态成员函数不接收 this 指针，无从访问。

自定义类的函数调用约定

默认约定：thiscall

  • 成员函数默认使用 thiscall：this 放 ECX，参数右到左入栈，被调用者平衡栈。

可以显式指定其他调用约定

  • 在成员函数声明前加 __stdcall / __cdecl 等，this 就会当作普通参数压栈传递。

__stdcall 成员函数的汇编特征

  • 明明只有 2 个参数，却压了 3 次栈、ret 0Ch 恢复 12 字节 → 说明多出的一个就是 this。
  • 逆向时看到”参数数量对不上（多一个）”，要考虑可能是非默认调用约定的成员函数。

小结

  • thiscall 不是铁律：成员函数可以显式指定 __stdcall、__cdecl 等约定。
  • 区别在于 this 的传递方式（寄存器 vs 压栈）和栈平衡责任方（被调用者 vs 调用者）。

附录二：核心结论速查

静态成员

  • 静态成员变量：所有实例共享一份内存（本质是全局变量），不占对象大小，无实例也能 类名::成员 访问；老语法必须在类外定义，C++17 用 inline static 类内定义。
  • 静态成员函数：无实例可调用；没有 this；不能访问非静态成员；不能用 const 修饰。

友元

  • friend 让类”单方面”开放私有成员；单向、不可传递、身份独立；破坏封装，慎用。

嵌套类 / 局部类

  • 嵌套类作用域归外层类，受外层类 public/private 管束；嵌套类能访问外层类私有（含静态），外层类不能访问嵌套类私有；局部类定义在函数内，成员必须全部类内定义，不能用静态成员。

内存三连（核心必背）

  1. malloc 只分配内存，new 分配内存 + 调构造函数；
  2. free 只释放内存，delete 释放内存 + 调析构函数；
  3. 类对象必须 new/delete 配对、new[]/delete[] 配对，不能混用 malloc/free。

底层视角（thiscall）

  • 成员函数：this 放 ECX，参数右到左入栈，被调用者平衡栈；成员访问 = this + 偏移。
  • 静态成员函数：不传 this，等价普通函数（调用者平衡栈）。
  • 静态成员变量：等价全局变量（固定地址）。
  • 编译器会删除”无意义的空构造函数”，需要初始化成员时才会生成。
  • 成员函数可显式改成 __stdcall 等约定，this 会改为压栈传递（栈多一个参数）。

运算符重载的概念（25:57）

什么是重载

  • 函数重载：同一个函数名，通过不同参数实现不同版本（如 Add 支持 int / float / double）
  • 运算符重载：让自定义类型（struct / class）的对象也能使用 + - * / < > 等运算符

两种实现方式

  1. 全局函数方式（非成员函数）
  • 两个参数：左操作数、右操作数
  • 访问私有成员 → 用 friend 友元声明
  1. 成员函数方式
  • this 是左操作数，括号里是右操作数
  • 定义在类外需要类名限定：bool Person::operator>(const Person& other) const { ... }

基本语法

  • operator 是关键字，固定写法
  • 一元运算符：全局函数 1 个参数 / 成员函数 0 个参数
  • 二元运算符：全局函数 2 个参数 / 成员函数 1 个参数（this 占左操作数）

关键点

  • 编译器把 a < b 翻译成 operator<(a, b)（全局）或 a.operator<(b)（成员）
  • 成员函数方式下，左操作数必须是类对象本身；全局函数可以支持左操作数类型转换

运算符重载的原则和时机

重载的意义

  1. 表达更直观：代码贴近自然语言（张三 + 李四 = 王五）
  2. 提升对程序的控制权：重载 new / delete，自定义内存分配、建立自己的缓冲区
  3. 提升可读性、可维护性（注意：不是提升开发效率，重载反而可能让开发变慢）

限制（必须记住）

  1. 不能自创运算符（不能发明 === 之类的新符号）
  2. 不能重载的运算符：
    • . 点运算符
    • :: 作用域解析运算符
    • sizeof 求大小运算符
    • ?: 条件（三目）运算符
  3. 不能修改运算符的优先级和结合性（a + b * c 永远是先乘后加）
  4. 不能修改操作数个数（二元就是 2 个、一元就是 1 个）
  5. 除了 new / delete，不能对原生类型（int、double 等）重载；只能对类或枚举类型重载
  6. C++17 起操作数计算顺序固定：按运算符本身顺序执行；C++17 之前 a + b + c 先算哪一个是未定义行为，由编译器决定

原则

  1. 不要改变运算符本身的意义：加法就是加法，别重载成减法（”养一只叫狗狗的猫”= 违背原意，代码让人迷惑）
  2. 不建议重载：
    • && / ||：会破坏短路求值（重载后两个操作数都会被求值）
    • & 取值运算符：破坏指针特性
    • , 逗号运算符

正确姿势

  1. 大部分运算符既能成员函数也能全局函数，优先重载为成员函数（为将来虚函数/接口扩展留余地；全局函数写死了不好扩展）

ostringstream 常用用法

本质

  • 头文件 <sstream>；像 cout 一样用 << 把各种类型写进内存里的字符串缓冲区，最后 .str() 取出 std::string。

核心 API

  • oss << 值：写入（支持 int/double/字符串/重载了 operator<< 的自定义类型）。
  • oss.str()：取出拼好的 std::string（返回拷贝）。
  • oss.str("")：清空内容，复用同一个 oss。
  • oss.clear()：复位流状态，搭配 str("") 一起用。

典型场景

  • 拼接字符串：oss << "姓名:" << name << ", 年龄:" << age;
  • 字符串和整数拼接：C++ 里 std::string 不能直接 + 整数，用 ostringstream 最自然：
  • 数字转字符串：oss << 3.14，比 to_string 更易加格式。
  • 格式化输出（需 <iomanip>）：
    • 保留两位小数：oss << std::fixed << std::setprecision(2) << pi;
    • 十六进制：oss << std::hex << std::showbase << 255;（→ 0xff）
    • 宽度补零：oss << std::setw(6) << std::setfill('0') << 42;（→ 000042）
  • 反向解析（istringstream）：iss >> a >> d >> word; 按空格把字符串拆成不同类型。
  • 自定义类型：重载 std::ostream& operator<<(std::ostream&, const T&) 后就能 oss << 对象。

常见坑：字符串不能直接 + 整数

  • 错误：std::string s = "等级" + 99; —— 这不是拼接，是对字符串字面量做指针运算（未定义行为）。
  • 写法一（纯字符串）：std::string s = "等级" + std::to_string(99);
  • 写法二（推荐，混排方便）：用 ostringstream：oss << "等级" << 99;

易错点

  • .str() 返回拷贝，改它不影响内部缓冲。

类型转换运算符

  • 写法：operator 目标类型()；只能是成员函数；不写返回类型但必须 return。
  • 解决二义性用 explicit（C++11），禁止隐式转换但允许显式强制。
  • 判空可重载 operator bool() 或 operator void*()。

游戏防修改

  • 加密整数：内存里存 真实值 ^ 密钥，读写时自动加解密；
  • 异或/加减可无损还原，乘除法不行。

递增递减

  • 前置：T& operator++()，无参，返回引用；
  • 后置：T operator++(int)，int 哑参仅用于区分，返回旧值副本；
  • 后置不要返回引用；类有指针成员时注意临时对象的深拷贝。

内存分配

  • new 三步：分配内存 → 调构造 → 返回地址；我们只能接管分配；
  • 重载 operator new(size_t) 就要配对重载 operator delete(void*)；
  • 数组版 new[]/delete[]、带参 placement new 也要成对；
  • 应用：对象池，预分配大内存，避免频繁 new/delete 造成碎片和性能损耗。

派生类对象 = 基类子对象 + 自己新增成员，大小严格叠加。

6. is-a vs has-a（设计原则，最容易错）

  • is-a（是一个）→ 用继承：人是动物；可见对象是对象；狼人是狼也是人。
  • has-a（有一个）→ 用组合/包含：人有胳膊；飞机有发动机、座位、空姐。

内存布局上这两种写法长得几乎一样（都是把另一个类的内存拼进来），区别完全在语义。判断口诀：能说”X 是一种 Y”就用继承，能说”X 有一个 Y”就用组合。

5. 私有继承的”代代相传”效应

一旦某一层用了 private 继承，基类的 public/protected 成员在这一层全部变 private，它的派生类再也访问不到，也无法通过再次 public 继承恢复。

6. 用 using 调整继承来的成员权限

规则：

  • 只能调整当前类能访问到的成员（基类的 private 成员改不了，因为你根本看不到它）；
  • 语法是 using 基类名::成员名;，后面不能写类型，不能写成 using Base::void f();；
  • 会把基类中所有同名函数一次性全部引入（相当于把它们拉进当前类作用域参与重载）。

7. 设计建议

  • 现代 C++ 工程里几乎只用 public 继承；
  • 数据成员尽量 private，通过 getter/setter 访问——便于加校验、下断点调试；
  • protected 虽然方便派生类直接访问，但也会破坏封装（派生类能直接改内部成员），谨慎使用；
  • private 继承表达”用基类的实现来复用代码”（implemented-in-terms-of），现代写法里优先用组合（把基类当成员对象）替代 private 继承。

从内存的角度理解继承

1. 单继承的内存布局

  • 基类子对象在前面，派生类新增成员在后面；
  • 所以构造必须从基类开始（前面那块先成型）；
  • 向上转型 Derived* → Base* 时，指针不用偏移（基类在最开头）。

2. 多重继承的内存布局

  • 第一个基类子对象在最前面；
  • 后续基类子对象依次排在后面；
  • 把 Woluman* 转成 Man* 时，编译器会自动加一个偏移，指到中间那块 Man 子对象。

3. 菱形继承的内存（普通继承，未虚继承）

两份 x,y 各占各的内存，所以 w.Wolf::x 和 w.Man::x 不联动。

4. 虚继承后的内存布局

关键点：

  • 每个虚继承路径的子对象前面多一个 vbptr（虚基表指针）；
  • 共享的虚基类子对象被挪到对象尾部；
  • 通过 vbptr → 表里的偏移 → 找到共享的 Animal 子对象，多了一层间接寻址，所以访问略慢；
  • 编译器帮你做的：w.x 不再是直接偏移，而是”沿着 vbptr 算一下再访问”。

5. 构造顺序 vs 内存位置（反直觉点）

虚继承下的表现
内存位置 共享的虚基类子对象在最后面
构造顺序 虚基类子对象最先构造（因为 B、C 都要共享它）
析构顺序 反过来：派生类 → B/C → 虚基类

也就是说：内存布局 ≠ 构造顺序。构造顺序由”谁先依赖谁”决定，不由谁在前在后决定。

6. 逆向分析视角（开发者彩蛋）

看一个陌生对象的内存：

  • 开头第一个成员如果是个指针，但你又没定义指针成员——大概率是 vptr（虚函数表指针，下一章多态讲）或 vbptr（虚基表指针）；
  • 顺着这个指针读出来的是一张偏移量表，表里那串数字（类似 1,6,5,4,8,5,2,10）就是到各虚基类子对象的偏移；
  • 看到这个结构，基本就能判定这个类用了虚继承 / 多态。

7. 多继承下的指针调整（this 偏移）

这也是为什么多重继承下 dynamic_cast 和交叉类型转换需要编译器帮忙调整指针。

  1. 继承 = 内存拼接，基类在前、派生类在后；多重继承按继承顺序依次拼接。
  2. 构造从最顶层基类开始，析构反过来。
  3. is-a 用继承，has-a 用组合——飞机不是发动机。
  4. private 成员”继承了但访问不到”，内存里仍占地方。
  5. 派生类同名函数会隐藏基类同名函数（不管参数是否相同），用 using 或 Base:: 救场。
  6. 多重继承要警惕二义性和菱形重复，必要时上 virtual 虚继承。

多态

知识点总结

  1. 什么是多态：同一个事物表现多种形态，多态建立在继承基础之上。分为两大类：对象多态、方法多态。
  2. 对象多态：派生类对象，可以用基类指针 / 引用表示。
    • 向上转型：子类 → 父类。人是动物，逻辑成立。子类指针/引用 → 基类指针/引用，支持隐式转换。
    • 向下转型：父类 → 子类。动物是人，逻辑不一定成立，没有隐式转换，需要强制转换。
    • ⚠️ 直接用对象拷贝赋值会发生内存切片（对象切片），子类多出的成员直接被切掉，丢失信息，无法实现多态。实现多态必须用指针或者引用。
  3. 方法多态
    • 静态多态（编译期多态）：编译阶段就确定调用哪个函数。代表：函数重载、模板。
    • 动态多态（运行时多态）：运行的时候才确定调用哪个函数。代表：虚函数。编译期无法确定对象真实类型。
  4. 实战场景举例：游戏里面怪物、NPC、玩家都继承同一个基类，统一放到基类指针数组，循环调用行为，不用写一大堆 if 判断区分对象类型。

通俗理解
对象多态：一个人，可以被叫做人、哺乳动物、动物，同一个实体，多种身份。
静态多态：函数重载，名字一样，参数不一样，编译就选好函数。
动态多态：同一个基类指针，指向不同子类，跑起来才知道执行谁的函数，需要虚函数。

    2. 派生类重写虚函数：参数列表必须和基类完全一致。参数不一样，不算重写，只是普通重载。
    3. 想要触发动态多态调用：必须使用基类指针 / 引用。直接对象.调用，静态绑定，不走虚表。
  3. 派生类重写虚函数的时候，virtual 可以省略，一旦基类是虚函数，派生类自动变成虚函数。建议写上 override，防止参数写错。

通俗理解：virtual 告诉编译器，这个函数不要编译期定死，等程序跑起来看对象真实类型，再决定调用哪个版本。

虚函数详解

知识点总结

** 1. override关键字（强烈推荐重写虚函数时加上）**

  • 写在派生类虚函数后面。作用：编译期校验，确认这个函数确实是重写基类虚函数。
  • 如果参数写错、名字写错，编译器直接报错，避免写出以为是重写实际是新函数的 bug。

注意：override 只是校验，不是改变运行行为，只是编译检查。

2. final关键字

  1. 修饰虚函数：virtual void f() final;，这个虚函数禁止后续子类继续重写。
  2. 修饰类：class A final{};，这个类禁止被继承。

3. 协变返回值（特殊例外）

重写虚函数，一般返回值要一样。例外：返回值是指针 / 引用，基类返回基类指针，派生类返回派生类指针（继承链条），允许不一样，叫做协变。

4. 访问权限坑

基类虚函数public，派生类重写改成private：

派生类对象直接.调用这个函数，编译报错（私有）。但是基类指针指向派生类，依然可以调用这个私有虚函数！绕过访问权限，破坏封装。
工程经验：基类虚函数尽量设计为private，避免这个坑。

5. ⚠️构造、析构函数内部调用虚函数

构造、析构里面调用虚函数，只会执行本类版本，不会动态多态！静态绑定！

  • 构造子类：先构造父类，父类构造的时候子类还没有构造出来，子类成员不存在，不能调用子类虚函数。
  • 析构子类：先析构子类，再析构父类；父类析构的时候子类已经销毁。

面试高频考点！

6. 虚函数默认参数

虚函数是动态绑定；默认参数是静态解析，编译期确定！
基类虚函数virtual void move(int x=10)；派生类重写写默认值x=20。
基类指针指向子类，调用move()，执行的是子类函数体，默认参数用的基类的 10，不是子类的 20！
工程建议：重写虚函数不要修改默认参数，产生难以排查 bug。

7. 虚析构函数

如果基类指针指向 new 出来的子类对象，执行delete 基类指针。基类析构不加 virtual，只会调用基类析构，子类析构不会执行，内存泄漏！

对象多态详解

知识点总结

  1. 向上转型：派生类 → 基类
  • public 公有继承，支持隐式转换。派生类* → 基类*，派生类& → 基类&。
  • 原理：继承内存布局，派生类内存开头完整包含基类子对象。
  • ❗禁止直接对象拷贝，会发生对象切片，子类独有的成员全部被切掉。
  1. 向下转型：基类 → 派生类
  • C++ 不允许隐式向下转型。编译器不知道基类指针实际指向的是基类对象，还是派生类对象。
  • 如果指针实际指向基类对象，强制当派生类用，访问子类成员，内存越界崩溃。
  • 需要手动强制转换。
  1. 三种强制转换：
    1. C 风格强制 (Derive*)pBase：暴力，绕过访问权限，风险极高。虚继承场景下会失效。
    2. static_cast<Derive*>(pBase)：编译期检查。要求继承是可访问（public），私有继承编译报错。运行期不校验对象真实类型，程序员自己保证安全。
    3. dynamic_cast<Derive*>(pBase)：运行时校验，需要类是多态类（有虚函数）。
  2. 多继承坑：多继承不同基类指针转换会自动调整指针偏移；千万不要用 void * 中转继承类指针，会丢失偏移信息，得到错误地址。

dynamic_cast 动态强制转换

知识点总结

dynamic_cast<目标类型>(变量)，运行时做类型安全检查。
✅硬性前提：源类必须是多态类（基类存在虚函数），依赖 RTTI 运行时类型信息，没有虚函数编译报错。

  1. 指针版本
    • 转换成功：返回合法目标指针；
    • 转换失败：返回nullptr空指针。可以 if 判空判断是否转换成功。
  1. 引用版本：没有空引用，转换失败直接抛出bad_cast异常。需要 try‑catch 捕获。
  2. 支持交叉转换 cross‑cast：多继承场景，同一个完整对象，两个没有直接继承关系的子对象之间转换，自动调整指针偏移。
  3. ❗工程忠告：不要大量写一堆 if + dynamic_cast 分支。这代表设计缺陷，优先把行为抽象为基类虚函数。只有迫不得已访问子类独有接口才使用。

typeid 调试多态，RTTI

知识点总结

  1. typeid(表达式) 返回std::type_info&，RTTI 运行时类型识别。
  2. 获取运行时动态真实类型条件：类必须是多态类（带虚函数）。
  3. ⚠️指针坑：typeid(p)拿到的是指针静态类型。想要拿到对象真实类型，必须解引用 typeid(*p)。
  4. .name()返回类型名字符串，仅供调试打印，不同编译器名字修饰不一样，禁止拿字符串做业务判断。
  5. 可以直接比较：typeid(*p) == typeid(Derive) 判断对象是不是这个类型。
  6. 引用不需要解引用，typeid(ref)直接拿到对象动态类型。
  7. 部分编译器需要手动开启 RTTI 编译选项。正式业务代码尽量少用，多用于调试。

抽象类

知识点总结

  1. 纯虚函数语法 virtual void func() = 0;
    • =0，没有函数实现体，只声明接口。
  2. 抽象类：包含至少一个纯虚函数的类
    • ❌不能实例化对象，不能Abstract a;。
    • ✅可以定义指针、引用，用于多态。
  3. 派生类继承抽象类：必须全部实现所有纯虚函数。只要有一个纯虚没有实现，派生类依旧是抽象类，不能实例化。
  4. 接口类（设计概念，C++ 没有 interface 关键字）：类里面几乎全部是纯虚函数，几乎没有成员变量，只定义接口规范，交给子类实现。Java/C# 有 interface 关键字。

用途：面向接口编程，团队开发，先定接口规范，不同人写不同实现。

  1. 抽象类构造建议写protected，禁止外部实例化，派生类可以调用。

类的成员函数的函数指针

知识点总结

  1. 普通函数指针不能接收非静态成员函数。非静态成员函数调用隐式携带this指针。
  2. 非静态成员函数指针语法
  1. 赋值：pFunc = &Wolf::func; 取地址&不能省略。
  2. 调用：必须绑定对象！两种运算符
    • 对象实例：(obj .* pFunc)();
    • 对象指针：(pObj ->* pFunc)();
    • 类内部：(this ->* pFunc)();
    • ⚠️括号不能省略，运算符优先级问题。
  3. 成员函数指针严格绑定类，不能指向别的类成员函数。
  4. static 静态成员函数没有 this 指针，可以直接用普通函数指针，不需要成员函数指针语法。

通俗理解：成员函数本身代码只有一份，存放在代码段。成员函数指针存的是函数入口地址；调用的时候必须传入对象（this），才能知道操作哪个实例的数据。
用途：框架回调，手动实现多态，逆向分析，日常业务写的不多。

虚函数的实现机制（底层原理 虚表 vtable、虚表指针 vptr）

知识点总结

  1. 只要类包含虚函数：对象内存最开头增加一个虚表指针 vptr
    • x86‑32 位：vptr 占 4 字节；x64‑64 位：vptr 占 8 字节。
    • vptr 放在对象内存头部，后面才放普通成员变量。
  2. 虚表 vtable
    • 每个类一张虚表，同一个类所有对象共享同一张虚表，不是每个对象一张虚表！
    • 虚表是一个函数指针数组，存放本类所有虚函数的地址。
    • 派生类重写虚函数：虚表对应数组下标位置替换为派生类函数地址；没有重写沿用基类地址。
  3. 虚函数指针调用汇编运行步骤：
  1. 获取对象起始地址；
  2. 对象头部读取 vptr 虚表指针；
  3. vptr 找到虚表 vtable；
  4. 根据虚函数下标偏移，取出虚函数地址；
  5. 跳转执行函数。

✨ 这就是动态多态：运行时查表，编译期不知道调用哪个函数。

  1. .直接对象调用虚函数：编译器知道对象确切类型，静态绑定，不走虚表查表。只有指针 / 引用调用虚函数，才走虚表实现动态多态。
  2. 虚表存放在只读内存段。正常程序不能修改；漏洞利用可以修改页属性篡改虚表劫持程序流程。
  3. RTTI（dynamic_cast、typeid）的类型信息，也存放在虚表相关结构里面。
